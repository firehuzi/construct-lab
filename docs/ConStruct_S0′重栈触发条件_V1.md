# ConStruct Lab · S0′ 重栈触发条件 V1

> 日期：2026-10-02 ｜ 状态：待评审
> 一句话：**写死一条可核的线 —— 到它就必须从 JSON 换成 PG/Neo4j。**
>
> **它的价值不在数字，在于【有一条线】**：否则我们会一直用轻栈做到某一天撞墙，
> **而那时不知道是哪一天开始不对的。**

---

## 〇、为什么必须先量现状，再写阈值

**拍一个「依据 >10 万条」的阈值谁都会写。而可核的意思是：它能从【现在】推出来。**

**实测（2026-10-02）：**

| | 现在 |
|---|---|
| 依据索引 | **8 条** ／ 7,725 字节 ⇒ **每条约 966 字节** |
| UCDP 提取 | 146,500 字节（126 双边对 ／ 1239 对-年 ／ 按州聚合） |
| 案例 | 6 个 ／ 66,861 字节 |
| 依据快照 | 8 个 ／ 1,062,813 字节（**平均 130 KB/条** —— 网页原文大） |

**推算（按每条约 966 字节的索引）：**

```
  1,000 条依据 ⇒ 索引约   0.9 MB
  5,000 条依据 ⇒ 索引约   4.6 MB
 20,000 条依据 ⇒ 索引约  18.4 MB
100,000 条依据 ⇒ 索引约  92.1 MB
```

---

## 一、三条触发线（可核）

### 线 1 · 依据条数 > 5,000

**依据**：索引是**全量加载进内存**的（`load_sources()` 一次读整个 `index.json`）。
5,000 条 ⇒ 约 4.6 MB ⇒ **加载与每次匹配都还无感**。
**越过这条线之后每一次 `case_check` 都要重读 4.6+ MB，且按 key 线性查。**

**⇒ 到 5,000 条：把索引迁到 SQLite**（不是 PG —— **SQLite 是单个文件，仍然符合「轻栈」的定义**）。
**⇒ 到 50,000 条：才谈 PG。**

**★ 这条线是【渐进的】，不是断崖。** 所以它写成两级。

### 线 2 · 启用信号层（GDELT / RSS 持续采集）

**依据**：**这是真正的体量驱动，而不是依据条数。**

```
GDELT 每天 10 万+ 事件；若启用，即便按【日增 1 万条】过滤后入库：
   一年 ⇒ 365 万条 ⇒ **远超 JSON 的量级**
```

**⇒ 只要信号层一开始持续采集（不是一次性研究），就必须上时序库（TimescaleDB）。**
**这条线【先于】线 1 到达，而且它是【开关式】的 —— 不是渐变，是打开就超。**

**★ 而信号层在今天（2026-10-02）**：
`collect_gdelt.py` 采集器**在**，但本地只有 **1 KB 的样例** —— **从未真跑过。**

### 线 3 · 需要多跳查询

**依据**：这三样 JSON 做不到，**而它们不是「慢」，是「做不了」**：

| 需求 | 为什么 JSON 做不了 | 需要 |
|---|---|---|
| **`A → B → C` 多跳** | 每跳都要全表扫；三跳就是三重循环 | **Neo4j** |
| **按时间窗聚合**（「近 90 天涉及 X 的信号」） | 无索引，每次全扫 | **TimescaleDB** |
| **同一实体的跨源合并去重** | 要靠图上的实体消解 | **Neo4j** |

**★ 这条线【不是按规模触发，是按需求触发】** —— **一旦有人问出一个多跳问题，就到了。**

---

## 二、三条线哪个先到

```
线 2（信号层开关）  ← 先到，而且是开关式的
      ↓
线 3（多跳需求）    ← 按需求触发，与规模无关
      ↓
线 1（依据 5,000）  ← 最后到，而且是渐进的
```

**⇒ 实际上，最可能先到的是【线 2】，而它取决于一个决定：**要不要启用信号层。
**而这个决定本身不属于 S0′** —— S0′ 只负责说「一旦启用，就到了」。

---

## 三、到线了要做什么（分两级，不是一步跳到底）

| 级别 | 触发 | 做什么 | 不做什么 |
|---|---|---|---|
| **L1** | 依据 > 5,000 | **`.json` → SQLite 单文件** | ⛔ 不上服务、不上 PG |
| **L2** | 信号层启用 ／ 多跳需求 | **SQLite → PG + TimescaleDB + Neo4j** | ⛔ 不重写判断逻辑（那是引擎侧的事） |

**★ L1 到 L2 之间刻意留了一级** —— 因为**「按条数增长」与「按需求突变」是两种不同的压力**，
用同一套方案应对会有一个是浪费的。

---

## 四、这条线本身怎么核

**三个数字进一份可复算的读数**（照《读数口径登记表》的写法）：

| 读数 | 怎么算 | 它实际量的是什么 |
|---|---|---|
| **依据条数** | `len(index.json["sources"])` | **索引里的条目数**（⛔ 不是快照文件数 —— 一条依据可能有多个快照） |
| **索引字节数** | `index.json` 的文件大小 | **全量加载的代价** |
| **信号条数** | —— **现在没有这个读数** | **一旦有，就是线 2 已经越过的证明** |

**★ 第三条现在【没有】—— 而它的缺失本身就是线 2 未到的证据。**
**（照《读数口径登记表》的规矩：没有的读数要写「没有」，不许让它看起来像 0。）**

**⇒ 建议加一条审计**：`s1.py --limits` 打出上面三个数并**直接判有没有越线**。
**理由与 `cwkb_audit.py` 同：一条线如果没人自动查，它就等于不存在。**

## 五、照实记

1. **本文件不写代码**（除了建议的那条 `--limits`）。
2. **线 1 的 5,000 是推算的**，依据是「每条约 966 字节」这个**实测值**与「几 MB 的索引还无感」这个判断。
   **后者是我的判断，不是实测** —— 要实测它得真造 5,000 条。**⇒ 照实标为判断。**
3. **线 2 与线 3 不依赖推算**，它们是**开关式**与**需求式**的 —— 只要发生，就是到了。
4. **⛔ 本文件不主张现在该上重栈。** 现在 8 条依据、6 个案例，轻栈完全够。
5. **⚠️ 而最该记的一条**：`collect_gdelt.py` 采集器**在**，本地却只有 **1 KB 样例** ——
   **它从未真跑过。** 也就是说 **线 2 离我们只有「跑一次采集」的距离，
   而那个距离上没有任何东西拦着。**
