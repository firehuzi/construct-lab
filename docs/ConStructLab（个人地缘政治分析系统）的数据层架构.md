### 二、给“从零到有”的COW底座三个工程化建议

既然COW是你亲手搭建的底层骨架，它必须被**硬编码**进系统的逻辑底层，绝不能和上层数据混在一起。以下是关键落地细节：

1.  **实体对齐（最苦的活，但必须做）**：
    - COW 使用**国家代码**（如 `CHN`、`USA`、`RUS`）。
    - GDELT 使用 **CAMEO 参与者编码**（如 `CHN`、`CHNGOV`、`CHNMIL`）。
    - **建议**：在数据库里新建一张 **`entity_ontology`（实体本体表）** ，手动建立 COW 代码与 GDELT 参与者的 **1对多映射**。这是你系统的“字典”，未来所有分析都靠它做归并。
    - *比如*：`COW_CHN` → `[GDELT_CHN, GDELT_CHNGOV, GDELT_CHNREB, ...]`

2.  **定义“基线状态”（Baseline Status）**：
    - COW 里包含“领土控制变更”和“同盟关系”的时间序列。
    - 将 **当前日期（2026年）** 的 COW 状态提取出来，作为系统的 **“默认地理政治基准”**。如果 GDELT 报道与基准冲突（例如宣称某地“自古以来”不受基准国控制），系统自动弹出提示：“**注意：该主张与历史法理基准（COW, 年份XXXX）不符**”。

3.  **分层存储策略（DuckDB 足矣）**：
    - **Base 表**（`cow_historical`）：只读，禁止程序自动修改（你手动维护）。
    - **Mid 表**（`ucdp_events`）：按年份索引，定期更新。
    - **Top 表**（`gdelt_pulse`）：每日增量追加，设置 30 天滚动删除（或压缩归档）。


### 三、如何与之前设计的“双环认知架构”结合？

之前 SVG 里的 **“信源 A/B/C”** 现在有了具体的物理意义：

- 当你在 **“外环（感知环）”** 输入一个 GDELT 热点事件时，AI 书记员的工作流应该是：
    1.  **查底层（COW）**：调出涉事双方的 200 年领土/同盟基线。
    2.  **查中层（UCDP）**：调出涉事双方近 40 年的实际冲突烈度曲线。
    3.  **展示上层（GDELT）**：展示今天的新闻标题。
- **AI 只负责把这三层数据并排陈列出来，不做任何“谁对谁错”的评价。**

**这就是“平”的认知**——让历史事实（COW）和当下噪音（GDELT）拥有同等发言权，由你的大脑做最终裁决。


### 四、承认现实：UCDP 和 GDELT 是“吃数据”的，COW 是“吃时间”的

- **COW 的痛苦**：编码标准老，领土变更数据需要人工核对（你“从零到有”指的大概就是这部分）。很苦，但它一旦建成，就是永久的个人智库资产。
- **建议的下一步**：将 COW 中的 **“国家间盟约矩阵”**（防御性同盟/中立/敌对）抽取出来，做成一个 **`static/` 目录下的 JSON 文件**。这样你未来用 Python 分析时，可以直接调用 `if ally(COW, 'A', 'B') == True`，不需要每次都查数据库。
